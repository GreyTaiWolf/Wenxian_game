# 《问仙》手游规划与开发路线

> 文档状态：执行基线  
> 适用仓库：`GreyTaiWolf/Wenxian_game`  
> 当前代码基线：React 18 + TypeScript strict + Vite 6，移动端优先、纯前端本地存档  
> 当前内容边界：炼气初期至筑基圆满，中州与南疆，修炼—探索—战斗—掉落—突破—宗门—洞府基础闭环

---

## 1. 执行结论

《问仙》不应推倒重做。当前仓库已经具备可持续迭代的核心数据层、状态层和移动端 UI，应采用“先完成单机竖切闭环，再手游化封装，最后扩内容与服务能力”的路线。

开发顺序必须遵守以下原则：

1. **先解决玩家不知道下一步做什么的问题。** 用主线目标串起已有修炼、任务、采集、战斗、突破、入宗与跨州内容。
2. **先让每个系统进入真实循环，再增加新系统。** 装备、任务、宗门、洞府都要具备来源、消耗、反馈和阶段目标。
3. **规则数据化，组件只负责展示与交互。** 境界、物品、敌人、任务、掉落、主线和地图均进入配置层；状态变化集中在 `src/game/`。
4. **先做稳定的 Web/PWA 单机版，再封装 Android/iOS。** 不在核心循环未稳定时过早引入原生插件、账号后端和商业化 SDK。
5. **每个里程碑必须可构建、可存档、可回归、可从新档玩通。** 不能只以“代码写完”作为完成标准。

本路线将项目分为九个里程碑：

```text
M0 工程基线
→ M1 新手主线竖切
→ M2 v0.1 核心闭环验收
→ M3 装备/战斗/任务深化
→ M4 宗门/洞府生产循环
→ M5 PWA 与移动端产品化
→ M6 结丹内容扩展
→ M7 Beta 质量与数据验证
→ M8 Android/iOS 封装与发布
```

| 世界地图 | 大世界、州域、地点、场景、纯文字格子、A* 寻路与行路异闻 | 高 |

### 2.2 主要缺口

| 缺口 | 玩家影响 | 优先级 | 处理方式 |
| --- | --- | --- | --- |
| 战斗掉落层级不完整 | 已于 v0.2.0 建立普通/精英/Boss 掉落表、首领保底与首通专属 | 已解决 | 后续继续审计来源矩阵 |
| 装备来源与替换节奏不足 | 装备数据丰富但真实投放不足 | P0 | 来源矩阵、对比提示、构筑验证 |
| 宗门和洞府偏展示 | 中长期留存目标不足 | P1 | 日常委托、兑换、设施、灵田、炼丹 |
| 缺少 PWA 能力 | 不能安装到桌面，离线首次启动能力不足 | P1 | manifest、Service Worker、缓存策略 |
| 存档只有本地浏览器 | 清缓存或换设备存在丢档风险 | P1 | 先导入/导出，后可选云存档 |
| 缺少单元与端到端测试 | 数值、迁移、战斗回归成本高 | P1 | Vitest + React Testing Library + Playwright |
| 缺少正式移动壳 | 尚非应用商店安装包 | P2 | 核心稳定后使用 Capacitor 封装 |
| 缺少运营与版本数据 | 无法判断卡点与留存 | P2 | Beta 阶段引入匿名、可关闭的事件统计 |

### 2.3 当前不做的范围

为防止范围失控，v0.x 阶段暂不开发：

- 实时多人、多人同屏、跨服战斗；
- 强制登录、复杂账号中心；
- 拍卖行、玩家交易和全服经济；
- 公会战争、赛季竞技；
- 抽卡、付费数值售卖；
- 大规模 3D 场景或即时动作战斗；
- 在核心玩法尚未稳定前建设重型微服务后端。

## 3. 产品定位

### 3.1 一句话定位

一款移动端优先的修仙文字 RPG：玩家用短操作完成修炼、探索和回合战斗，以境界、装备、宗门、洞府及跨州剧情形成长期成长。

### 3.2 核心体验支柱

1. **短反馈：** 每次聚气、采集、对话和战斗都在数秒至数分钟内给出清晰结果。
2. **长成长：** 境界、寿元、装备构筑、宗门身份、洞府设施共同形成数小时至数周目标。
3. **有方向的探索：** 地图不是地点列表，而是由任务、资源、风险与剧情驱动的路线选择。
4. **可理解的修仙规则：** 玩家应知道突破为什么成功或失败、装备为何更强、某地为何危险。
5. **单机友好：** 不依赖持续联网也能完成核心内容；联网能力用于更新、备份和可选服务。

### 3.3 玩家循环

#### 30 秒循环

```text
查看目标 → 点击一次行动 → 获得文字/数值反馈 → 决定下一行动
```

#### 5 分钟循环

```text
接任务 → 前往地点 → 采集/战斗/对话 → 交付 → 获得成长资源
```

#### 30–60 分钟循环

```text
积累修为与材料 → 调整装备/技能 → 挑战精英或秘境 → 完成突破
```

#### 日循环

```text
洞府结算 → 宗门委托 → 指定资源路线 → 装备强化/炼丹 → 推进主线
```

#### 周期循环

```text
完成一个大境界 → 解锁新系统与州域 → 建立新资源闭环 → 挑战阶段 Boss
```

## 4. 版本目标

### 4.1 v0.1：可稳定玩通的炼气—筑基闭环

必须实现：

- 新建角色后持续显示当前推荐目标；
- 中州新手链：聚气、任务榜、灵药谷、黑风山、突破、古修洞府、入宗；
- 炼气初期至筑基初期至少能在正常游玩中完成；
- 任务、战斗和秘境可稳定提供突破材料；
- 装备可获得、比较、穿戴并明显改变战斗结果；
- 存档刷新后状态一致；
- 构建、数据检查和关键流程测试通过。

### 4.2 v0.2：筑基阶段与南疆完整闭环

必须实现：

- 筑基初期至圆满内容节奏；
- 南疆悬赏、精英、秘境、材料和装备来源；
- 宗门任务、贡献兑换与职位第一版；
- 洞府灵田、聚灵阵、炼丹第一版；
- PWA 安装、离线启动和存档导入/导出；
- Android 内测包。

### 4.3 v0.5：结丹 Beta

必须实现：

- 结丹四阶段、阶段 Boss 和至少一个新州域；
- 功法/神通/法宝构筑第一版；
- 完整数据校验、自动化测试和内容制作模板；
- 可选云存档与版本更新提示；
- 性能、无障碍、兼容性和崩溃恢复达到 Beta 标准。

### 4.4 v1.0：正式发布

必须实现：

- 炼气、筑基、结丹三大阶段内容完整且平衡；
- 中州、南疆与第三州域形成差异化生态；
- 主线、支线、宗门、洞府、装备和战斗互相供给；
- Android/iOS 发布流程、隐私说明、存档保障和客服入口完整；
- 建立版本更新、热修复、内容验收和回滚机制。

## 5. 技术路线

### 5.1 平台路线

#### 阶段 A：移动 Web/PWA

保留现有 React/Vite 技术栈，先补齐：

- Web App Manifest；
- Service Worker 与版本化静态缓存；
- iOS/Android 安全区适配；
- 横竖屏策略；
- 安装提示与离线状态提示；
- 存档导入、导出和损坏恢复；
- 静态资源体积与加载监控。

#### 阶段 B：Android 壳

核心循环稳定后接入 Capacitor 类原生壳，首批只使用：

- 状态栏、安全区与启动屏；
- Android 返回键；
- 文件保存/分享，用于存档备份；
- 本地通知，用于闭关完成提醒；
- 应用版本、更新提示和日志导出。

任何原生插件都必须通过接口封装，Web 环境必须保留降级实现。

#### 阶段 C：iOS 壳

Android 内测稳定后再处理：

- iOS 安全区、键盘和滚动行为；
- 后台恢复；
- 文件导入/导出；
- 本地通知权限；
- 应用商店元数据与隐私声明。

### 5.2 目标目录结构

```text
src/
├─ app/                  # 应用启动、平台适配、错误边界
├─ components/           # 纯 UI 与轻交互组件
├─ features/             # 按功能组织的页面级模块（逐步迁移）
│  ├─ cultivation/
│  ├─ combat/
│  ├─ exploration/
│  ├─ inventory/
│  ├─ quest/
│  ├─ sect/
│  └─ cave/
├─ data/                 # 静态配置与内容表
├─ game/                 # 纯规则、状态变化、迁移和计算
├─ platform/             # Web/PWA/Capacitor 能力适配
├─ persistence/          # 存档、导入导出、云同步接口
├─ validation/           # 数据配置与存档校验
├─ tests/                # 跨模块测试夹具与端到端场景
└─ types.ts              # 当前共享类型；后续按领域拆分
```

不要求一次性重构。新增功能先遵守边界，旧文件在触及业务时渐进迁移。

### 5.3 分层规则

#### 数据层 `src/data/`

负责声明：

- 境界、技能、物品、敌人、掉落；
- 地图、地点、场景、任务、主线；
- 品级、词条、价格和生成规则；
- 所有可由策划调整的常量。

禁止在数据层直接读取浏览器 API 或修改状态。

#### 规则层 `src/game/`

负责：

- 输入旧 `GameState`，返回新 `GameState`；
- 战斗、奖励、突破、任务、时间、装备和存档归一化；
- 尽可能使用纯函数；
- 随机逻辑逐步支持注入随机源，便于测试重放。

禁止在规则层渲染 JSX 或直接操作 DOM。

#### UI 层 `src/components/` / `src/features/`

负责：

- 展示当前状态；
- 收集玩家操作；
- 调用规则层函数；
- 提供加载、禁用、错误和成功反馈。

禁止在组件内复制数值公式或维护另一套真实游戏状态。

#### 持久化层

负责：

- 存档读取、写入和版本迁移；
- JSON 导入/导出；
- 校验、备份和恢复；
- 后续本地与云端存档冲突策略。

### 5.4 状态修改规范

所有状态写入必须满足：

1. 不直接修改传入对象；
2. 奖励、消耗、日志和时间推进尽量复用统一助手；
3. 同一行为不得在 UI 与规则层重复推进时间；
4. 任务完成、掉落、突破等关键行为必须可测试；
5. 新增存档字段必须提供默认值、旧档迁移和异常值归一化；
6. 不将可实时派生的数据永久存档，避免数据漂移。

## 6. 核心系统开发路径

### 6.1 主线、任务与新手引导

#### 第一阶段：当前目标卡

- 从现有状态推导当前阶段，不增加存档字段；
- 显示章节、目标、地点、行动、收益、进度和下一解锁；
- 点击目标可切换到对应功能模块；
- 高境界旧档自动跳过已完成的新手阶段。

#### 第二阶段：正式任务链

新增任务配置能力：

- `prerequisites`：前置任务、境界、物品、地点、阵营；
- `objectives`：采集、击杀、对话、到达、穿戴、突破、设施升级；
- `rewards`：资源、装备池、声望、解锁、剧情标记；
- `repeatability`：一次性、每日、每周、冷却；
- `failure`：时限或特殊失败条件；
- `tracking`：可追踪目标与导航提示。

#### 第三阶段：章节与剧情状态

- 主线章节单独配置；
- NPC 对话按任务状态分支；
- 关键机缘和 Boss 奖励只能领取一次；
- 剧情标记集中管理，禁止继续借任务进度字段表达所有标记；
- 完成章节时展示解锁摘要。

### 6.2 修炼与境界

开发顺序：

1. 验证炼气—筑基的修为时长、材料来源和灵石消耗；
2. 为突破准备界面补充来源提示；
3. 增加伤势、心境、不稳的恢复渠道；
4. 让闭关、丹药、功法和宗门共同影响修炼效率；
5. 结丹前引入大境界专属试炼，而不是只点击概率按钮；
6. 所有突破公式建立自动化边界测试。

验收重点：

- 不存在无法通过正常玩法获得的必需材料；
- 失败惩罚有压力但不会形成不可恢复死档；
- 每个小境界至少解锁一个新目标、资源层或构筑选择；
- 旧档属性归一化后不会超过合理边界。

### 6.3 战斗

#### v0.1

- 普通、精英、Boss 三层敌人；
- 明确显示速度顺序、目标、伤害、闪避、暴击和状态；
- 战斗胜利进入统一结算页；
- 失败提供返回城镇、恢复与重试路径；
- 自动战斗只操作最新状态，且可随时停止。

#### v0.2

- 状态效果统一模型：持续时间、叠层、来源、驱散；
- 敌人技能权重、阶段行为与 Boss 转阶段；
- 队伍站位或前后排的轻量策略；
- 构筑统计：总伤害、治疗、承伤、回合数；
- 可注入随机种子，支持战斗重放与回归测试。

#### v0.5

- 功法、神通、法宝之间形成至少三种可验证构筑；
- 敌人具有针对性而非单纯数值膨胀；
- 高难内容提供推荐战力与机制提示，但不硬锁唯一答案。

### 6.4 掉落与装备

必须建立统一掉落表：

```text
敌人/任务/宝箱
→ 掉落池
→ 次数与权重
→ 保底与唯一奖励
→ 生成装备实例
→ 背包与结算展示
```

装备开发步骤：

1. 普通怪稳定提供基础材料，低概率掉落凡品/良品装备；
2. 精英提供指定部位、精品装备或任务材料；
3. Boss 提供关键突破材料、灵品装备和首次唯一奖励；
4. 背包显示与已穿装备的属性差异；
5. 过高境界装备显示封印与实际生效属性；
6. 建立回收/出售/分解，解决库存膨胀；
7. 后续强化只增加可控成长，不绕过阶位规则。

每个境界阶段必须维护“来源矩阵”：

| 阶段 | 商店 | 普通怪 | 精英 | Boss/秘境 | 任务 |
| --- | --- | --- | --- | --- | --- |
| 炼气初期 | 基础白装 | 材料/白装 | 绿装 | 少量蓝装 | 新手装备 |
| 炼气中期 | 白/绿装 | 材料/绿装 | 蓝装 | 蓝/紫装 | 指定部位 |
| 炼气后期/圆满 | 绿/蓝装 | 蓝装 | 蓝/紫装 | 紫装/筑基材料 | 突破准备 |
| 筑基 | 筑基基础装 | 材料/绿装 | 蓝/紫装 | 紫装及以上 | 构筑装备 |

### 6.5 世界、地图与探索

每个州域必须先回答五个问题：

1. 该州域服务哪个境界阶段？
2. 它与上一州域相比新增什么风险？
3. 它稳定产出哪些突破、装备和设施资源？
4. 哪些势力、NPC 和任务构成叙事主轴？
5. 完成州域后把玩家引向哪里？

地图功能开发顺序：

- 地图层只使用纯文字格子、地形状态、地点锚点、角色位置和 A* 路径，不再加载大世界或州域背景图；
- 主线目标提供地点文本和可选导航高亮；
- 移动过程触发统一旅行事件；
- 事件按区域、时间、天气、境界和标记筛选；
- 宝箱、机缘、采集点增加冷却或一次性标记；
- 地图调试工具只在开发模式显示；
- 触摸选格、路径预览、移动步进、目标标记和地图容器滚动在真机回归。

### 6.6 宗门

宗门 V1：

- 每日委托三选一；
- 贡献兑换基础丹药、材料和功法残页；
- 外门—内门—核心身份条件；
- 宗门声望影响兑换与剧情；
- 每项内容明确每日上限和刷新时间。

宗门 V2：

- 藏经阁：功法学习与升级；
- 执事关系与个人支线；
- 宗门试炼 Boss；
- 宗门设施对修炼、炼丹、洞府提供加成；
- 可切换宗门前必须处理声望、贡献和剧情后果。

### 6.7 洞府、灵田与炼丹

开发顺序：

1. 闭关离线收益可预览、可结算、可中止；
2. 聚灵阵升级拥有明确材料来源和收益曲线；
3. 灵田加入种植槽、成熟时间、收获与种子来源；
4. 炼丹加入配方、材料、成功率、品质和批量制作；
5. 洞府设施之间形成循环：探索得材料 → 升设施 → 提高产出 → 支持突破；
6. 离线结算设置合理上限，避免更改系统时间获得无限收益；
7. 所有计时使用统一世界时间或可靠时间源，不在各组件独立计算。

### 6.8 经济系统

经济至少包含：

- 灵石：通用交易与突破成本；
- 宗门贡献：宗门限定兑换；
- 地区声望：地区内容和商店解锁；
- 材料：突破、设施、炼丹和任务消耗；
- 装备：战斗构筑与回收价值。

调平原则：

- 每项货币至少有两个来源、两个长期消耗；
- 关键突破材料必须有可预期来源，随机掉落只作为加速；
- 商店不能直接抹掉探索和战斗价值；
- 重复任务收益不得比主线首次奖励更高；
- 装备分解产物不能无损循环制造；
- 所有价格与掉落修改同步记录在 `docs/BALANCE.md`。

## 10. 测试与质量策略

### 10.1 测试金字塔

#### 规则单元测试

优先覆盖：

- 境界查找、阶段比较、突破成功/失败边界；
- 奖励增加、资源消耗、负数与异常值；
- 装备生成、穿戴要求、属性合成；
- 任务前置、目标进度和完成结算；
- 主线阶段推导；
- 时间推进、冷却和离线收益；
- 存档归一化与版本迁移；
- 战斗行动、状态效果和胜负结算。

随机逻辑必须允许传入固定随机源，测试不能依赖偶然结果。

#### 数据校验测试

CI 中检查：

- ID 唯一；
- 所有引用目标存在；
- 任务前置没有循环；
- 掉落物品、敌人技能、地图地点均存在；
- 境界顺序、成本、成功率和属性为有限数；
- 装备部位、阶位、品级与属性规则一致；
- 关键突破材料至少存在一个稳定来源；
- 首次唯一奖励不能被普通重复池无限获取。

#### 组件集成测试

覆盖：

- 主线卡随状态变化；
- 任务接取/完成按钮状态；
- 突破材料选择与禁用条件；
- 背包装备对比与穿戴；
- 战斗按钮只在合法回合可用；
- 存档删除、导入、错误提示。

#### 端到端测试

至少维护以下场景：

1. 新建角色 → 聚气 → 接采药任务 → 采集 → 交付；
2. 接黑风任务 → 战斗 → 交付 → 首次突破；
3. 古修洞府 → 获得筑基丹 → 入宗；
4. 刷新页面 → 继续当前存档；
5. 旧版存档迁移 → 属性、装备、地图和时间正常；
6. 南疆进入 → 完成两项悬赏；
7. 离线缓存 → 断网启动；
8. 导出存档 → 清空 → 导入恢复。

### 10.2 缺陷等级

| 等级 | 定义 | 发布规则 |
| --- | --- | --- |
| P0 | 丢档、无法启动、主线阻断、无限资源、严重安全问题 | 立即阻断合并与发布 |
| P1 | 核心系统错误、战斗无法结束、关键奖励缺失、重大布局不可用 | 候选版本前必须清零 |
| P2 | 次要逻辑、文本、视觉、非主路径兼容问题 | 可进入明确排期 |
| P3 | 优化建议、轻微体验与未来增强 | 放入产品待办 |

### 10.3 合并门禁

每个 PR 至少满足：

- `yarn build` 通过；
- 新增规则有测试或明确说明测试缺口；
- 玩法或数值变化同步文档；
- 存档字段变化包含迁移；
- 不引入未使用依赖；
- 不破坏旧档；
- PR 描述写明动机、变更、验证和风险；
- 与正在进行的重复 PR 冲突时先整合而不是并行复制。

### 10.4 设备回归矩阵

目标覆盖：

- 小屏 Android；
- 主流 Android 竖屏；
- 大屏 Android；
- 带安全区的 iPhone；
- iPad/平板基本可用；
- 桌面 Chrome/Edge 用于开发与调试；
- Safari 用于 PWA 与安全区回归。

重点验证：触摸目标、底部导航、安全区、文字格选点与路径、地图容器滚动、异闻/结算弹窗滚动、键盘遮挡、后台恢复和低内存重载。

### 10.5 性能目标

以下均作为发布目标而非当前测量结果：

- 首屏脚本和可选地点场景资源按需加载；
- 文字格选点与地图滚动保持流畅，不在每次指针移动中执行重型路径计算；
- 单次状态更新避免复制无关大对象；
- 战斗日志和世界日志设置长度上限；
- 格子地图只渲染必要的可视信息，避免在低端机持续绘制无关装饰层；
- 构建时监控 bundle 体积变化；
- 低端设备上不因品级动画产生持续高负载；
- 系统“减少动态效果”设置关闭非必要动画。

## 11. 存档与数据安全

### 11.1 版本策略

当前根存档版本为 V4。V4 在旧字段之外新增待处理路途异闻、异闻历史、事件标记、战斗组胜场和战后结算；V1–V3 加载时由归一化补齐默认值。新增字段不得破坏既有角色、装备实例、任务、地图落点和世界时间。

每次存档结构变化：

1. 增加明确版本；
2. 保留最近至少三个版本的迁移路径；
3. 先复制原始存档作为备份；
4. 逐版本迁移，不直接跨越多个版本猜测结构；
5. 迁移后执行归一化和数据校验；
6. 失败时保留原始数据并提示导出诊断文件。

### 11.2 导入导出

导出文件建议包含：

- 游戏标识；
- 应用版本；
- 存档版本；
- 导出时间；
- 校验摘要；
- 存档主体。

导入必须验证：

- JSON 格式；
- 游戏标识；
- 支持的存档版本；
- 必填字段与数值边界；
- 槽位覆盖确认；
- 迁移与恢复结果。

### 11.3 云存档决策门

只有在以下条件满足后引入云存档：

- 本地导入/导出稳定；
- 存档版本迁移有自动化测试；
- 能明确处理设备 A/B 同时离线修改的冲突；
- 有账号、隐私、删除和数据导出方案；
- 后端成本与维护责任明确。

云端同步默认不应覆盖本地较新档；冲突时展示角色、境界、时间和更新时间供玩家选择。

## 13. 数值与平衡流程

### 13.1 建立基准角色

每个小境界维护三种角色快照：

- 基础装：正常主线最低配置；
- 标准装：完成该阶段主要任务后的预期配置；
- 优秀装：完成精英/秘境后的配置。

所有敌人、掉落和突破成本以这些快照验证，而不是凭单件装备数值判断。

### 13.2 战斗目标区间

为每类战斗定义目标：

- 普通战：低风险、稳定资源；
- 精英战：需要合理技能/装备，失败可恢复；
- Boss：验证阶段机制与构筑；
- 越级战：允许尝试，但奖励不应鼓励无成本反复重开。

每次平衡改动记录：角色快照、敌人、回合数、胜率样本、资源消耗和奖励价值。

### 13.3 经济回归

每次版本至少验证：

- 从新档到首次突破所需行动量；
- 各阶段灵石收入与必要支出；
- 关键材料期望获取次数；
- 任务、商店、战斗、洞府的收益占比；
- 装备库存增长与回收能力；
- 离线收益是否挤压主动玩法。

## 15. 版本与协作流程

### 15.1 分支规范

- `main`：始终可构建、可部署；
- `feat/<scope>`：功能；
- `fix/<scope>`：缺陷；
- `docs/<scope>`：文档；
- `chore/<scope>`：工程维护；
- 自动化代理分支可使用 `codex/<scope>`。

### 15.2 PR 规范

PR 必须包含：

- Motivation：为什么做；
- Description：做了什么；
- Data/Save Impact：数据与存档影响；
- Testing：执行了什么验证；
- Screenshots：可视变化；
- Risks/Rollback：风险和回滚方式；
- Related Issues：关联问题。

### 15.3 提交规范

建议使用：

- `feat:` 新功能；
- `fix:` 缺陷；
- `docs:` 文档；
- `test:` 测试；
- `refactor:` 不改变行为的重构；
- `style:` 视觉样式；
- `ci:` 工作流；
- `chore:` 维护。

### 15.4 发布流程

```text
功能 PR 合并
→ main CI
→ Pages 预览验证
→ 版本冻结
→ 全流程回归
→ 生成候选版本
→ 真机测试
→ 发布
→ 监控与缺陷分流
```

发布必须保留上一稳定版本的构建产物和回滚说明。

## 16. Definition of Done

一个功能只有同时满足以下条件才算完成：

- 玩家入口明确；
- 正常路径、失败路径和重复路径都定义；
- 数据配置与规则实现分离；
- UI 有加载、禁用、成功和失败反馈；
- 存档兼容已处理；
- 规则测试或可复现验证存在；
- 移动端触摸与滚动可用；
- 文档同步；
- CI 构建通过；
- 没有新增 P0/P1 缺陷；
- 可以从新档或测试夹具到达该功能；
- 能说明该功能的资源来源、消耗和长期价值。

## 17. 风险登记

| 风险 | 概率 | 影响 | 预防措施 | 触发后处理 |
| --- | --- | --- | --- | --- |
| 继续加数据但缺少玩法闭环 | 高 | 高 | 新内容必须填写来源/用途/验收 | 暂停扩表，先补投放与任务 |
| 大组件持续膨胀 | 高 | 中高 | 新规则移入 `game/`，功能渐进拆分 | 按触及区域拆分，不全量重写 |
| 存档迁移破坏旧档 | 中 | 极高 | 版本迁移测试、原档备份 | 回滚版本，提供恢复工具 |
| 随机突破/掉落造成卡死 | 中 | 高 | 稳定来源、保底和失败恢复 | 调整来源并补偿受影响存档 |
| 重复 PR 和分支冲突 | 中高 | 中 | 开工前检查已有 PR/Issue | 关闭重复项，保留单一实现 |
| PWA 缓存旧版本 | 中 | 高 | 版本化缓存、更新提示、回退 | 清理失效缓存，恢复上一版本 |
| 原生封装过早拖慢玩法 | 中 | 高 | M5 前不引入大量原生依赖 | 回退 Web 接口，延后插件 |
| 数值膨胀失控 | 高 | 高 | 基准角色、来源矩阵、回归脚本 | 冻结新境界，先重做曲线 |
| 格子地图信息过密导致小屏难读 | 中 | 中高 | 文本层级、路径高亮、移动端真机回归 | 降低同屏标签并提供列表入口 |
| 缺少真实玩家验证 | 中 | 高 | v0.1 后尽早小规模测试 | 根据卡点调整主线和资源 |
